# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## на разработку информационной системы «Внутренний библиотечный учет»

### 1. ВВЕДЕНИЕ
**1.1. Цель проекта**
Автоматизация процессов внутреннего учета фонда библиотеки, обеспечение централизованного хранения метаданных о книгах, авторах и сопутствующих лицах, а также предоставление инструментария для быстрого поиска и аналитики для зарегистрированных пользователей (библиотекарей).

**1.2. Область применения**
Система предназначена для внутреннего использования сотрудниками библиотеки. Система должна поддерживать одновременную работу нескольких независимых пользователей с разграничением доступа на основе аутентификации.

### 2. АРХИТЕКТУРА И ТЕХНОЛОГИЧЕСКИЙ СТЕК
Система строится по клиент-серверной архитектуре с разделением на фронтенд и бэкенд.

**2.1. Клиентская часть (Frontend)**
*   **Фреймворк:** Angular (последняя стабильная версия).
*   **Язык:** TypeScript.
*   **UI-библиотека:** Angular Material или PrimeNG (для обеспечения единообразия интерфейса, таблиц, форм и модальных окон).
*   **Управление состоянием:** RxJS, NgRx (опционально, для сложных состояний).

**2.2. Серверная часть (Backend)**
*   **Язык и стандарты:** Java (17+), Jakarta EE (Web Profile).
*   **Сервер приложений:** WildFly.
*   **Архитектура:** RESTful API.
*   **ORM:** Jakarta Persistence API (JPA) / Hibernate.
*   **Безопасность:** Jakarta Security, JWT (JSON Web Tokens) для аутентификации и авторизации.

**2.3. Система управления базами данных (СУБД)**
*   **СУБД:** PostgreSQL (версия 14+).
*   **Требования:** Поддержка транзакций, целостности данных (Foreign Keys), индексов для ускорения поиска.

### 3. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

#### 3.1. Управление пользователями (Библиотекарями)
*   Регистрация и аутентификация пользователей (email + пароль).
*   Хранение паролей исключительно в хэшированном виде (BCrypt).
*   Ведение журнала действий: каждая запись в БД должна содержать информацию о том, каким пользователем (`added_by`) она была создана.

#### 3.2. Управление справочниками и сущностями (CRUD)
Система должна предоставлять интерфейсы для создания, чтения, обновления и удаления (CRUD) следующих сущностей:
*   **Отделы (SECTION):** Название, индекс ББК (Библиотечно-библиографическая классификация).
*   **Серии (SERIES):** Название серии.
*   **Авторы (AUTHOR), Переводчики (TRANSLATOR), Иллюстраторы (ILLUSTRATOR):** Фамилия, Имя, Отчество. Должна быть реализована защита от дублей (поиск существующего ФИО перед созданием).
*   **Книги (BOOK):** Полный набор библиографических данных (название, город, издательство, год, том, количество страниц, ISBN, номер редакции/издания, примечание). Статусы: доступна/не доступна, наличие иллюстраций.
*   **Подработы (SUBWORK):** Название, привязка к конкретной книге и автору подработы (для сборников и многотомников).

#### 3.3. Подсистема поиска и фильтрации
Реализовать механизм **расширенного поиска** с поддержкой следующих критериев (как по отдельности, так и в любых логических комбинациях):
*   Поиск по названию книги (полное и частичное совпадение / LIKE).
*   Поиск по ФИО автора.
*   Поиск по названию отдела.
*   Поиск по названию серии.
*   Поиск по ФИО иллюстратора.
*   Поиск по ФИО переводчика.
*   *Дополнительно:* Фильтрация по году издания, наличию (статус `is_available`), наличию иллюстраций.
*   Результаты поиска должны выводиться с поддержкой пагинации и сортировки.

### 5. ТРЕБОВАНИЯ К ПОЛЬЗОВАТЕЛЬСКОМУ ИНТЕРФЕЙСУ (FRONTEND)
**5.1. Общие требования:**
*   Адаптивная верстка (Responsive Design) для работы на мониторах ПК и планшетах.
*   Использование SPA (Single Page Application) подхода для минимизации перезагрузок страниц.

**5.2. Компоненты интерфейса:**
*   **Дашборд / Главная страница:** Краткая статистика (кол-во книг, отделов), быстрый доступ к поиску.
*   **Формы ввода (Reactive Forms):** Строгая валидация на стороне клиента (обязательные поля, формат года, формат ISBN, проверка длины строк).
*   **Таблицы данных (Data Tables):** Отображение списков книг, авторов и т.д. с возможностью сортировки по колонкам, пагинацией и кнопками действий (Редактировать, Удалить).
*   **Панель расширенного поиска:** Выпадающие списки (Select) для выбора отделов, серий, авторов и текстовые поля для ввода названий/ФИО. Динамическое добавление условий фильтрации.

### 6. ТРЕБОВАНИЯ К СЕРВЕРНОЙ ЧАСТИ И API (BACKEND)
**6.1. REST API:**
*   API должно быть спроектировано по принципам REST.
*   Формат обмена данными: JSON.
*   Использование HTTP-методов по назначению (GET для чтения, POST для создания, PUT/PATCH для обновления, DELETE для удаления).
*   Эндпоинты должны быть сгруппированы по ресурсам (например, `/api/v1/books`, `/api/v1/authors`).

**6.2. Обработка данных и транзакции:**
*   Использование `@Transactional` для обеспечения целостности данных при создании сложных сущностей (например, создание Книги с одновременным созданием новых Автора и Переводчика).
*   Оптимизация запросов к БД: использование `JOIN` и `FETCH` (например, `@EntityGraph` или `JOIN FETCH` в JPA) для предотвращения проблемы N+1 при загрузке списков книг с их авторами и отделами.

**6.3. Безопасность и валидация:**
*   Валидация входящих DTO (Data Transfer Objects) с использованием Jakarta Validation (`@NotNull`, `@Size`, `@Pattern`).
*   Защита от SQL-инъекций (обеспечивается JPA/Hibernate).
*   Защита от XSS (обеспечивается встроенными механизмами Angular и экранированием на бэкенде).
*   Все эндпоинты, кроме `/api/v1/auth/**`, должны быть защищены и требовать валидный JWT-токен.

### 7. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ
**7.1. Производительность:**
*   Время отклика API при стандартных операциях (CRUD) не должно превышать 500 мс.
*   Время выполнения сложного комбинированного поиска не должно превышать 2 секунд (обеспечивается правильным проектированием индексов в PostgreSQL).

**7.2. Логирование и мониторинг:**
*   На уровне WildFly и приложения должно быть настроено логирование ошибок (ERROR) и предупреждений (WARN).
*   Логирование действий пользователей (INFO) при критических изменениях (удаление книг, изменение статусов).

**7.3. Развертывание (Deployment):**
*   Приложение должно собираться в WAR-архив (для бэкенда) и статические файлы (для фронтенда).
*   Наличие `Dockerfile` и `docker-compose.yml` для быстрого развертывания связки WildFly + PostgreSQL + Nginx (для Angular).
*   Наличие скриптов миграции базы данных (например, Flyway или Liquibase) для автоматического создания и обновления схемы БД при первом запуске.

### 8. ЭТАПЫ РАЗРАБОТКИ
1.  **Проектирование:** Утверждение ТЗ, детализация API (Swagger/OpenAPI), финализация схемы БД.
2.  **Настройка окружения:** Инициализация репозиториев, настройка CI/CD, поднятие БД и сервера приложений.
3.  **Разработка Backend:** Создание сущностей JPA, репозиториев, сервисов, REST-контроллеров, настройка безопасности (JWT).
4.  **Разработка Frontend:** Верстка базового layout, реализация модулей авторизации, CRUD-таблиц и форм.
5.  **Интеграция и Поиск:** Связывание фронтенда и бэкенда, реализация и оптимизация механизма комбинированного поиска.
